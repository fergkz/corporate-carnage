# TODO-011 — Modo de qualidade gráfica reduzida para dispositivos fracos

**Status**: concluído

**Pedido original**: no relatório de playtest entregue a Fernando, o assistente apontou que "ainda não foi medido o desempenho em computadores/celulares fracos" como pendência para o lançamento online do jogo (item já citado antes no [CONTEXT.md](../CONTEXT.md), seção "Próximas evoluções possíveis": "Medir FPS em computadores e celulares usados no evento"). Fernando pediu para transformar esse achado (e os outros do mesmo relatório) em itens de backlog — aqui documentado como a contrapartida de implementação (uma opção de qualidade reduzida), já que "medir FPS" em si é uma ação de teste, não uma mudança de código.

**Situação atual**:
- `render()` ([public/game.js:1137-1178](../public/game.js)) roda a cada frame via `requestAnimationFrame` (linha 1690) e, além de desenhar todas as entidades (`drawZombies`/`drawPlayers`/`drawPickups`/`drawCorpses`/etc.), recalcula por frame — mesmo quando nada mudou na cena estática:
  - `burnExploredMask()` + `renderRememberedLayer()` (linhas 1148-1150): a camada "lembrada" do fog-of-war (ver [CONTEXT.md](../CONTEXT.md), seção "Reformulação... TODO-004") redesenha chão+paredes+props inteiros num canvas offscreen **todo frame**, mesmo que o jogador não tenha se movido o suficiente para revelar área nova.
  - `clipToVisionCone()` (linha 1156) e `drawFogOfWar()` (linha 1175) recalculam um `createRadialGradient` a cada frame para a vinheta de visão.
  - Vários efeitos visuais (escudo, boost de visão, granada armada, chama de disparo, explosão) também criam um `ctx.createRadialGradient(...)` novo a cada frame em vez de cachear (grep encontrou 10 chamadas a `createRadialGradient` espalhadas pelo arquivo, cada uma potencialmente executada por frame para cada entidade ativa desse tipo).
  - `ctx.imageSmoothingEnabled = false` já está configurado (mantém pixel art nítido, também mais barato que suavização) e o pixel ratio já é limitado: `const dpr = Math.min(devicePixelRatio || 1, 2)` ([public/game.js:147](../public/game.js)) — ou seja, já existe uma otimização de resolução, só falta um modo mais agressivo (dpr=1) para hardware realmente fraco.
- Não existe hoje nenhuma opção de qualidade gráfica no jogo (nem detecção automática, nem toggle manual) — o cliente sempre roda no nível de detalhe máximo implementado.
- O servidor já roda a simulação num tick fixo de 20Hz (`TICK_RATE = 20`, [server.js:15](../server.js)) independente do hardware do cliente — o gargalo de desempenho num dispositivo fraco é 100% do lado do render Canvas 2D no cliente, não da rede/simulação.

**Pesquisa externa**:
- Práticas gerais para Canvas 2D em dispositivos fracos (ver [Konva Performance Tips](https://konvajs.org/docs/performance/All_Performance_Tips.html), [HTML5 Canvas Performance Gist](https://gist.github.com/jaredwilli/5469626) e [Code Theory — Optimizing HTML5 Canvas](https://codetheory.in/optimizing-html5-canvas-to-improve-your-game-performance/)): reduzir/desativar sombras e gradientes complexos em hardware fraco, cachear em canvas offscreen tudo que não muda frame a frame (o jogo já faz isso para sprites — ver "Sprites reais integrados" no CONTEXT.md — mas não para a camada "lembrada" do fog-of-war), evitar recriar gradientes todo frame quando o resultado visual é o mesmo, reduzir resolução interna (pixel ratio) em vez de depender só de CSS para redimensionar, e limitar a quantidade de partículas/efeitos simultâneos.
- Conclusão prática: os pontos de maior custo identificados no código atual (recomposição total da camada "lembrada" todo frame, gradientes recriados por entidade/frame) são exatamente os alvos que essas referências recomendam atacar primeiro — cache/throttle antes de qualquer coisa mais drástica como remover recursos visuais inteiros.

**Proposta técnica**:
- Adicionar um nível de qualidade (`'high' | 'low'`, guardado em `localStorage` e ajustável por um toggle simples no HUD ou na tela inicial) que, quando `'low'`:
  1. **Throttle da camada "lembrada"**: só rodar `burnExploredMask()`/`renderRememberedLayer()` a cada N frames (ex. 1 a cada 4) em vez de todo frame — a camada representa área já visitada, então uma atualização discretizada não é perceptível, e isso elimina o redesenho mais caro identificado.
  2. **Reduzir `dpr` para 1** mesmo em telas com pixel ratio maior (linha 147), cortando a quantidade de pixels renderizados por frame proporcionalmente ao quadrado do ratio.
  3. **Simplificar gradientes de glow**: trocar `createRadialGradient` por um preenchimento sólido semi-transparente (`ctx.fillStyle = 'rgba(...)'`) nos efeitos decorativos (escudo, boost de visão, chama de disparo) — mantém a legibilidade do efeito (ainda dá pra ver "esse jogador tem escudo") a um custo de renderização bem menor; **não** mexer no fog-of-war principal (`drawFogOfWar`) nesse modo, porque ele é a mecânica de visão limitada, não só decoração.
  4. **Reduzir tempo de vida/quantidade de partículas**: encurtar a duração de `bloodBursts`/manter só 1 `bloodStain` por morte em vez de sortear entre as 5 variações (o sorteio em si não é caro, mas o desenho de decalques acumulados no chão é uma fonte razoável de overdraw ao longo de uma partida longa).
- Detecção automática (opcional, mais arriscada): medir o tempo entre frames nos primeiros segundos de partida (`dt` já é calculado no loop de `animate`) e sugerir automaticamente o modo `'low'` se a média ficar consistentemente abaixo de ~45-50 FPS — mas isso exige cuidado para não alternar de qualidade no meio de uma partida de forma perceptível; mais seguro é medir antes de "Iniciar operação" (na tela de lobby) e aplicar a partir do próximo `render()`.
- Antes de qualquer mudança de código, medir com o Chrome DevTools Performance/FPS meter (ou o `stats.js` equivalente manual, dado que não há dependência nova desejada) num notebook/celular real de gama baixa para confirmar que os pontos acima são de fato o gargalo antes de otimizar às cegas — o diagnóstico acima é por leitura de código, não por profiling real ainda.
